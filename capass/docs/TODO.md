## 1. ツールサーバ側の「受け口」を、CaPassクライアントで提供する

### 1.1 背景: ツールの種別と、受け口

- CaPassサーバがツールサーバへ中継する方法は、**HTTPS(REST)のみ**です(`toolservers/register` で登録した「実行URL」へ、`POST`)。
- ただし、**ツール自体の種別は、REST APIに限定されません。** CLI、REST API、A2A、DBのコマンドなど、何でも対象にできます。実行URLで待ち受けて、受け取ったリクエストを、ツールの種別に合わせて変換する「**受け口(アダプタ)**」が、ツールサーバ側にあれば足ります。
- 受け口の仕様(CaPassサーバからの呼び出し)は、QUICKSTART の 5.7 のとおりです。受け口は、いまは、**ツール提供者が自分で実装**する必要があります(見本: [`examples/fake_tool_server.py`](../examples/fake_tool_server.py))。

### 1.2 案: ツールサーバにインストールするCaPassクライアントに、受け口(アダプタ)の機能を持たせる

ツール提供者がHTTPサーバを実装しなくて済み、トークンの検証などの安全に実装すべき部分を、共通の実装にできます。

- **動作のイメージ:** ツールサーバ上で、CaPassクライアントを「受け口モード」で常駐させる(コマンド名は仮: `capass serve`)。実行URLは、この受け口のURLになる。
- **受け口がやること:**
  1. `Authorization: Bearer` のツール代理トークンを、ツールサーバ付きDB(`[認証情報/ツール代理トークン/AIエージェント情報]`)と照合する(定数時間で比較する。トークンはハッシュで保存する)
  2. `tool_endpoint` が、トークンに紐づくものと一致することを確認する(トークンは、ロール(ツール)単位で、AIエージェントには紐づかない。`agent_id` は、受け口のログに残す)
  3. `params` を、ツールの `params_schema` で再検証する(CaPassサーバでも検証済みだが、ツールサーバ側でも行う)
  4. 認証情報の権限(スコープ)の範囲内かを確認する(範囲外なら403)
  5. `tool_endpoint` ごとの設定に従って、ツールを実行し、結果を返す
- **`tool_endpoint` ごとの設定(例: 設定ファイル):** ツールの種別(`cli` / `rest` / `a2a` など)、実行方法、使う認証情報(Principal/Credential)、`params_schema`、`context`(説明)。この設定から、`addtool` の登録も自動化できる。
  - `cli`: コマンドと引数を組み立てて実行する。**シェルを経由せず**、paramsの値は引数として渡す(コマンドインジェクション対策)。
  - `rest`: ツールのREST APIを、認証情報で呼び出す。
  - `a2a`: ツールのエージェントを、認証情報で呼び出す。
- **シーケンス図との関係:** `chtkn`(トークンの定期更新)、`list registered`、`update lock` など、ツールサーバ側のCLIの機能と、同じ設定・同じツールサーバ付きDBを共有できる。

### 1.3 決めること・論点

- 常駐サービスになるため、待ち受けポート、TLS(証明書)、プロセス管理(systemd、コンテナなど)をどうするか。ツール提供者が、自分で用意するのか。
- 受け口が、ネットワークに公開されるプログラムになるので、そのセキュリティ(入力サイズの制限、同時実行数の制限、ログにトークンを出さない)をどう担保するか。
- ツール提供者が、受け口を自前で実装する場合の仕様(QUICKSTART 5.7)は、今後も維持するか(クライアント提供の受け口は、あくまで任意の選択肢にするか)。
- **方式は、CaPassサーバが、ツールサーバの受け口へ、HTTPSで中継する形(push型)とする。** ツールサーバ側から、実行依頼を取りに来る方式(pull型)は、採用しない(AIエージェントへの応答に、待ちが増え、ストリーミングで中継しにくくなるため)。

### 1.4 呼び出し元がCaPassサーバであることの確認(受け口の必須要件)

**背景:** ツール代理トークンは、ロール(ツール)単位で、AIエージェントには紐づかない。受け口が、トークンだけで実行を受け付けると、**トークンを盗んだ人が、ツールサーバへ直接リクエストを送れば、任意の `agent_id` で、ロールのスコープの範囲のツールを実行できる**。そのため、受け口は、「呼び出し元が、本当にCaPassサーバか」を、トークンとは別に確認する必要がある。

**方針: 受け口(CaPassクライアントの受け口モード)に、次を必須にする。**

1. **暗号学的な呼び出し元の確認(どちらか、または両方):**
   - **CaPassサーバの署名(webhookの署名と同じ形):** CaPassサーバが、ツールサーバへのリクエストに、サーバ自身の鍵で署名する。署名対象は、`agent_id`、`tool_endpoint`、`params`、署名時刻、`nonce`、送り先(ツールサーバ)。受け口は、CaPassサーバの公開鍵で検証し、署名時刻の許容範囲と、`nonce` の再利用を確認する(再送と、paramsの改ざんを防ぐ)。**トークンだけでは受け付けない**(トークンと署名の、両方が必要)。
   - **mTLS:** CaPassサーバにクライアント証明書を持たせ、受け口が、その証明書を検証する。
2. **ネットワークでの制限(多層防御):** ファイアウォール(セキュリティグループなど)で、受け口のポートへの接続元を、CaPassサーバのIPアドレスに限る。ただし、これは認証ではない(同じセグメント内でのなりすまし、NATや共有の出口IPなど、限界がある)。
3. **受け口だけを入口にする:** ツール本体(DB、CLI、REST API)は、受け口からだけ到達できるようにする(ループバックやUnixソケットで待ち受ける、ファイアウォールで限る、など)。受け口の検査を、迂回できないようにする。
4. **ポートを占有(待ち受け)しているだけでは、認証にならない。** ポート番号を固定しても、そのポートに接続できる相手は、限られない。接続元のポート番号は、偽装できる。

**CaPassサーバ側の前提(実装が必要):**

- CaPassサーバの署名鍵(秘密鍵の保管、ローテーション)。公開鍵を、ツールサーバ(受け口)へ配る方法(CaPassクライアントの設定時に固定(ピン留め)する、CaPassサーバのTLS接続で取得する、など)と、鍵の更新手順。
- 署名のフォーマットの定義(署名プレフィックス、正規化JSON)。いまの、AIエージェント・ツールサーバ・管理者の署名と同じ規則に揃える。
- `exec` の中継(`call_tool_server`)で、リクエストに署名を付ける。

**決めること:**

- 呼び出し元の確認の方式(CaPassサーバの署名、mTLS、または両方)。
- CaPassサーバの署名鍵の管理方法(ローテーション、複数台構成での共有)。
- 受け口のログに、`agent_id` を残す(リソース側のログには、ロールの主体しか残らないため)。
- **限界:** ツールサーバのホスト自体が侵害された場合は、受け口の検査を迂回して、認証情報へ直接アクセスされるので、この仕組みでは防げない(ホストの防御は、別途必要)。

## 2. CaPassクライアント(CLI)

シーケンス図の各サブコマンド。暫定クライアント(`examples/provisional_client.py`)が代用している部分は、CLIで置き換える。

| サブコマンド | 役割 | 対応するAPI |
|---|---|---|
| `keygen` | 公開鍵/秘密鍵の作成(ツールサーバ、AIエージェント、管理者) | なし(ローカル) |
| `regist` | ツールサーバ/AIエージェントの初回登録、ツール(ロール単位)の登録、AIエージェントへの割り当ての申請 | `toolservers/register`、`agents/register`、`tools/addtool`、`agents/{agent_id}/grant/{tool_endpoint}` |

| `exec` | ツールの実行(AIエージェント側) | `agents/{agent_id}/exec/{tool_endpoint}` |
| `chtkn` | ツール代理トークンの更新(ツールサーバの定期更新ジョブ。割り当てられた全AIエージェントに反映される) | `tools/{tool_endpoint}/chtkn` |
| `chkey` | ツールサーバのリプレース(予約は管理者、切り替えは旧・新の署名、切り戻しは旧の署名) | `toolservers/{toolserver_id}/replace/reserve` `/replace/activate` `/replace/rollback` |

| 管理者用 | 承認(`approve`)、割り当ての承認・取り消し、予約(`replace/reserve`)、承認待ち一覧 | `toolservers/{toolserver_id}/approve`、`agents/{agent_id}/approve`、`agents/{agent_id}/grant/{tool_endpoint}/approve`、`agents/{agent_id}/revoke/{tool_endpoint}`、`toolservers/{toolserver_id}/replace/reserve` |

- AIエージェント側のCLI(`list executable` / `exec`)は、**`params_schema` を、AIエージェントが使うツール定義(MCPの `inputSchema` など)へ、そのまま渡せる形で出力する**と、AIエージェントが扱いやすい。
- 秘密鍵の保管場所(ファイル権限、OSのキーストアなど)を決める。

## 4. 承認まわり

- 承認待ち一覧のAPI(公開鍵、申請者メアド、実行URLの表示)。いまは、管理者がSQLで確認している。
- 承認時の公開鍵の照合(承認する対象の公開鍵を、管理者が明示して、DBの値と一致することを確認する)。
- `revoked` にするAPI。いまはSQLで更新している。
- 申請者メールアドレスの確認(いまは自己申告)。許可するドメインの制限など。
- 予約(`reserved`)や待機(`standby`)を、期限の前に取り消すAPI(いまはSQLで `revoked` にする)。ツールサーバのリプレースの、承認待ち・予約の一覧API。切り替え・切り戻しの監査ログ(誰が、いつ、どのツールサーバからどのツールサーバへ)。

### 4.1 WebUIと利用者(将来)

- **AIエージェントの利用者が、WebUIから、ツールの割り当て(`grant`)を申請し、その上司などが承認する形を目指す。** いまは、申請者メールアドレス(`applicant_email`)と、承認者メールアドレス(`approver_email`。承認したCaPassサーバ管理者)を、割り当て(`tbl_agent_tool`)に記録している。
- **利用者のテーブルとログイン機能を作り、メールアドレスの文字列を、利用者への参照に置き換える。** ログインは、自前のパスワード認証ではなく、社内のIdP(SSO / OIDC)を使う。申請者の自己申告(確認されていないメールアドレス)の問題も、これで解決する。
- 承認者は、申請者の上司などを、社内のディレクトリ(IdPのグループ、人事データなど)から決める。**申請者と承認者が、同じ人にならない**ようにする(職務の分離)。申請・承認・取り消しの通知(メール、チャット)と、監査ログも必要。
- WebUIの認証(セッション)と、いまの署名による認証(CLI・機械向け)は、併存させる。承認の処理(service層)は、承認者の種類(管理者の鍵、ログインした利用者)によらず、共通にする。

## 5. その他

- **DBのマイグレーション:** 現状は、`create_all`(既存のテーブルは変更されない)のみ。Alembicなどの導入。
- **レート制限の共有:** 初回登録APIのレート制限は、プロセスのメモリ上。複数プロセス・複数台構成では、共有ストア(Redisなど)が必要。
- **ツール代理トークンの暗号鍵:** 環境変数ではなく、KMSなどで管理する。
- **ツールサーバへの接続:** 接続の再利用(コネクションプール)や、非同期化が必要になったら、標準ライブラリの `urllib` から、HTTPクライアントのライブラリ(httpxなど)への置き換えを検討する。
- **`params` のサイズ上限:** `exec` のボディのサイズに、上限を設ける。
