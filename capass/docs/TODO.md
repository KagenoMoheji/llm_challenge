## 1. ツールサーバ側の「受け口」を、CaPassクライアントで提供する

### 1.1 背景: ツールの種別と、受け口

- CaPassサーバがツールサーバへ中継する方法は、**HTTPS(REST)のみ**です(`toolservers/register` で登録した「実行URL」へ、`POST`)。
- ただし、**ツール自体の種別は、REST APIに限定されません。** CLI、REST API、A2A、DBのコマンドなど、何でも対象にできます。実行URLで待ち受けて、受け取ったリクエストを、ツールの種別に合わせて変換する「**受け口(アダプタ)**」が、ツールサーバ側にあれば足ります。
- 受け口の仕様(CaPassサーバからの呼び出し)は、QUICKSTART の 5.7 のとおりです。受け口は、いまは、**ツール提供者が自分で実装**する必要があります(見本: [`examples/fake_tool_server.py`](../examples/fake_tool_server.py))。

### 1.2 案: ツールサーバにインストールするCaPassクライアントに、受け口(アダプタ)の機能を持たせる

ツール提供者がHTTPサーバを実装しなくて済み、トークンの検証などの安全に実装すべき部分を、共通の実装にできます。

- **動作のイメージ:** ツールサーバ上で、CaPassクライアントを「受け口モード」で常駐させる(コマンド名は仮: `capass serve`)。実行URLは、この受け口のURLになる。
- **受け口がやること:**
  1. `Authorization: Bearer` のツール代理トークンを、ツールサーバ付きDB(`[認証情報/ツール代理トークン/AIエージェント情報]`)と照合する(定数時間で比較する。トークンはハッシュで保存する)
  2. `agent_id` と `tool_endpoint` が、トークンに紐づくものと一致することを確認する
  3. `params` を、ツールの `params_schema` で再検証する(CaPassサーバでも検証済みだが、ツールサーバ側でも行う)
  4. 認証情報の権限(スコープ)の範囲内かを確認する(範囲外なら403)
  5. `tool_endpoint` ごとの設定に従って、ツールを実行し、結果を返す
- **`tool_endpoint` ごとの設定(例: 設定ファイル):** ツールの種別(`cli` / `rest` / `a2a` など)、実行方法、使う認証情報(Principal/Credential)、`params_schema`、`context`(説明)。この設定から、`addtool` の登録も自動化できる。
  - `cli`: コマンドと引数を組み立てて実行する。**シェルを経由せず**、paramsの値は引数として渡す(コマンドインジェクション対策)。
  - `rest`: ツールのREST APIを、認証情報で呼び出す。
  - `a2a`: ツールのエージェントを、認証情報で呼び出す。
- **シーケンス図との関係:** `chtkn`(トークンの定期更新)、`list registered`、`update lock` など、ツールサーバ側のCLIの機能と、同じ設定・同じツールサーバ付きDBを共有できる。

### 1.3 決めること・論点

- 常駐サービスになるため、待ち受けポート、TLS(証明書)、プロセス管理(systemd、コンテナなど)をどうするか。ツール提供者が、自分で用意するのか。
- 受け口が、ネットワークに公開されるプログラムになるので、そのセキュリティ(入力サイズの制限、同時実行数の制限、ログにトークンを出さない)をどう担保するか。
- ツール提供者が、受け口を自前で実装する場合の仕様(QUICKSTART 5.7)は、今後も維持するか(クライアント提供の受け口は、あくまで任意の選択肢にするか)。
- **別の方式の検討:** ツールサーバ側から、CaPassサーバへ、実行依頼を取りに来る方式(pull型)。ツールサーバが、待ち受けポートを開けなくてよくなる反面、CaPassサーバに、依頼のキューと、結果を受け取る仕組みが必要になる。

## 2. CaPassクライアント(CLI)

シーケンス図の各サブコマンド。暫定クライアント(`examples/provisional_client.py`)が代用している部分は、CLIで置き換える。

| サブコマンド | 役割 | 対応するAPI |
|---|---|---|
| `keygen` | 公開鍵/秘密鍵の作成(ツールサーバ、AIエージェント、管理者) | なし(ローカル) |
| `regist` | ツールサーバ/AIエージェントの初回登録、ツールの追加 | `toolservers/register`、`agents/register`、`agents/{agent_id}/addtool` |
| `list executable` | 使用できるツールの一覧(AIエージェント側) | `agents/{agent_id}/tools` |
| `exec` | ツールの実行(AIエージェント側) | `agents/{agent_id}/exec/{tool_endpoint}` |
| `chtkn` | ツール代理トークンの更新 | 未実装(3.を参照) |
| `chkey` | ツールサーバ公開鍵の更新(リプレース) | 未実装(3.を参照) |
| `list registered` | ツールサーバが、登録内容(利用日時など)を取得 | 未実装(3.を参照) |
| `update lock` | ツールサーバが、ツールをロックする | 未実装(3.を参照) |
| 管理者用 | 承認(`approve`)、承認待ち一覧、`revoke` | `toolservers/{toolserver_id}/approve`、`agents/{agent_id}/approve` |

- AIエージェント側のCLI(`list executable` / `exec`)は、**`params_schema` を、AIエージェントが使うツール定義(MCPの `inputSchema` など)へ、そのまま渡せる形で出力する**と、AIエージェントが扱いやすい。
- 秘密鍵の保管場所(ファイル権限、OSのキーストアなど)を決める。

## 4. 承認まわり

- 承認待ち一覧のAPI(公開鍵、申請者メアド、実行URLの表示)。いまは、管理者がSQLで確認している。
- 承認時の公開鍵の照合(承認する対象の公開鍵を、管理者が明示して、DBの値と一致することを確認する)。
- `revoked` にするAPI。いまはSQLで更新している。
- 申請者メールアドレスの確認(いまは自己申告)。許可するドメインの制限など。
- 承認済みのツールサーバが、承認済みの任意のAIエージェントにツールを追加できる現状に対して、AIエージェント提供者の同意を確認する仕組み。

## 5. その他

- **DBのマイグレーション:** 現状は、`create_all`(既存のテーブルは変更されない)のみ。Alembicなどの導入。
- **レート制限の共有:** 初回登録APIのレート制限は、プロセスのメモリ上。複数プロセス・複数台構成では、共有ストア(Redisなど)が必要。
- **ツール代理トークンの暗号鍵:** 環境変数ではなく、KMSなどで管理する。
- **ツールサーバへの接続:** 接続の再利用(コネクションプール)や、非同期化が必要になったら、標準ライブラリの `urllib` から、HTTPクライアントのライブラリ(httpxなど)への置き換えを検討する。
- **`params` のサイズ上限:** `exec` のボディのサイズに、上限を設ける。
